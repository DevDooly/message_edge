# Notification Edge 서명키 교체 실행서

## 1. 목적과 현재 상태

현재 소스와 CI 로그에는 키스토어 및 비밀번호가 포함되지 않는다. 다만 과거 공개 Git 기록에 기존 릴리스 키가 포함되었으므로, 이 키는 더 이상 비밀이라고 간주할 수 없다.

2026-09-04에 자체 배포 APK용 Android 서명 계보를 생성했다. `v1.3.16`부터 API 28 이상은 새 인증서, API 26~27은 기존 설치 호환용 인증서를 사용한다. 공개 Git 이력 강제 재작성은 서명 회전과 별개이며 아직 수행하지 않았다.

## 2. 선택한 전환 방식

GitHub Releases에서 APK를 직접 배포하므로 Play App Signing이 아닌 `apksigner` 서명 계보 방식을 사용한다.

- 패키지명 `com.devdooly.notificationedge`를 유지한다.
- API 28 이상은 회전된 새 인증서를 사용한다.
- API 26~27은 서명 계보를 지원하지 않으므로 기존 인증서로 업데이트 호환성을 유지한다.
- 태그 배포 전 API 26과 35에서 직전 릴리스 위에 후보 APK를 실제 덮어쓰기 설치한다.
- 기존 키에 롤백 권한을 부여하지 않아 회전 후 지원 플랫폼에서 기존 키가 다시 주도권을 얻지 못하게 한다.
- Git 이력 강제 재작성은 모든 태그·포크·협업자에 영향을 주므로 별도 유지보수 작업으로 남긴다.

## 3. 고려한 전환 방식

### 방식 A: 기존 설치 호환성 우선

- 기존 서명키를 오프라인 비밀 저장소와 CI Secrets에서만 제한적으로 사용한다.
- 저장소 최신 상태와 빌드 로그에는 키·비밀번호를 남기지 않는다.
- 인증서 지문 고정, APK SHA-256 게시, 업데이트 앱의 패키지·버전·서명 검증을 유지한다.
- 공개된 키 자체의 위험은 해소되지 않으므로 임시 운영 방식으로 취급한다.

### 방식 B: 새 키와 새 패키지로 완전 전환

- 새 애플리케이션 ID와 새 서명키를 사용한다.
- 기존 앱과 별도 설치되며 설정과 알림 접근 권한을 다시 구성해야 한다.
- 기존 사용자를 새 앱으로 안내하는 마지막 공지 릴리스를 기존 키로 배포한다.
- 전환 완료 후 기존 업데이트 채널을 읽기 전용 또는 종료 상태로 바꾼다.

### 방식 C: 배포 플랫폼의 공식 키 교체 절차 사용

- Google Play 등 실제 배포 플랫폼의 키 업그레이드·업로드 키 재설정 절차를 따른다.
- 플랫폼이 제공하는 기기별 호환성 범위를 확인하고 API 26·27 업데이트 시험을 별도로 수행한다.
- 플랫폼 콘솔의 승인 완료 전에는 CI의 인증서 기준값을 변경하지 않는다.

### 방식 D: 자체 배포 APK 서명 계보 사용 — 선택

- 기존 키와 새 키로 Android `SigningCertificateLineage`를 생성한다.
- `--rotation-min-sdk-version 28`로 API 28 이상에서 새 인증서를 사용한다.
- API 26~27에서는 기존 인증서를 유지해 재설치 없이 업데이트할 수 있게 한다.
- 기존 키가 노출된 API 26~27의 위험은 기술적으로 완전히 제거할 수 없으므로 지원 종료 또는 새 패키지 전환 전까지 잔여 위험으로 기록한다.

## 5. 완료 기준

- 승인된 서명 계보로 서명된 후보가 API 26과 API 35의 설치·업데이트 정책을 만족한다.
- CI에는 승인된 기존·새 인증서 지문만 남고 키 원문은 저장소와 로그에 없다.
- 기존 키의 보관·폐기 상태와 Git 이력 정리 결과가 감사 가능한 문서로 남는다.
- 사용자에게 재설치, 데이터 초기화, 권한 재승인이 필요한지 릴리스 노트에 명확히 안내한다.
